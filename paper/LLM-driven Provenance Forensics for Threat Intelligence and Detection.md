
## 1. 这篇论文在解决什么问题

### 1.1 背景：APT 取证很难

论文关注的是 APT 这类**多阶段、隐蔽、持续时间长**的攻击。传统安全分析面对这类攻击时，最大的难点不是“有没有日志”，而是：

* 日志和 provenance 数据量太大，可能每天几十亿事件；
* 攻击步骤被故意伪装成正常行为；
* 分析员需要手工写查询、手工拼接证据、手工构造攻击叙事；
* 现有 provenance-based IDS 多偏向“检测分数”，不擅长输出**可解释、可核验的取证结论**；
* 外部威胁情报（CTI 报告）和内部系统证据之间缺乏自动联动。

论文明确指出，现有流程存在三大瓶颈：

1. **可扩展性差**：数据太大，人工或传统 ML 流水线处理成本高；
2. **上下文整合弱**：不能很好地把 CTI 报告里的 IOC/TTP 自动映射到系统证据；
3. **推理支持不足**：面对复杂多阶段攻击，缺乏自动化的多步调查与验证能力。

---

## 2. 论文的核心想法是什么

作者提出 **PROVSEEK**：一个由 LLM 驱动的、带多代理协同和多工具链的取证框架。

它不是简单“问 LLM：我是不是被攻击了？”，而是让 LLM 扮演一个**调查控制器**：

1. 先理解用户问题；
2. 从 CTI 报告里抽取可能相关的进程、文件、IP 等 IOC；
3. 把这些 IOC 转成针对 provenance 数据库的精确查询；
4. 查到系统证据后再继续追问、补查；
5. 只有当结论能被具体事件 ID / 边 ID / 节点 ID 支撑时，才输出最终结论。

论文中很强调一个词：**verification-first**。
也就是说，LLM 不是“凭语言能力生成答案”，而是**每一步都要绑定可验证的系统证据**。如果证据不足，系统要明确说“不够”，并触发 follow-up 调查。这个设计是整篇论文最关键的思想之一。

## 3. PROVSEEK 的整体架构

论文第 4 页的图 2 和图 3 给了整体流程图。系统主要由**3 个 Agent + 3 个核心模块**组成。

### 3.1 三个 Agent

#### （1）Investigation Agent

这是“首席调查员”。

职责是：

* 理解分析员意图；
* 收集初始证据；
* 判断当前证据是否足够回答问题；
* 如果不够，就把任务交给 Follow-Up Agent。

它会调用一批工具，例如：

* Provenance SQL Explorer
* Artifact Lookup
* Event Lookup Resolver
* CTI Retriever
* Plan Generator

论文还提到它会用不同的角色提示词，比如：

* “你是 DFIR 分析师”
* “你是系统安全专家”
* “你是安全审计员”

这种 role specialization 的目的是让同一个 LLM 在不同阶段具备不同的“专业视角”。

#### （2）Follow-Up Agent

这是“补证据调查员”。

当初始证据不够时，它会：

* 生成下一步调查计划；
* 继续围绕进程 / 文件 / IP 做更有针对性的查询；
* 根据中间结果动态调整方向；
* 直到找到足够证据，或耗尽步数预算。

它的作用很像人工取证时的“顺藤摸瓜”：

* 先找到 `/var/log/xdev`
* 再发现还缺 `/var/log/wdev`
* 再继续找写入/删除它的进程
* 再关联可疑网络连接

这就是论文所说的**bounded CoT reasoning loops**：有限步数的链式追踪推理。

#### （3）Safety Agent

这是“证据审计员”。

它不是查攻击，而是审查答案：

* 这条结论有没有具体 edge/node ID 支撑？
* 有没有过度自信？
* 有没有把猜测说成事实？
* 有没有缺少必要 caveat？
* 建议的应急动作是否安全？

如果 Safety Agent 认为答案证据不足，会把结果标成 **FLAGGED**，再触发 Follow-Up Agent 补证据。
只有通过审计后，结果才会标成 **SAFE**。论文第 20–21 页给了这个闭环提示模板，非常能体现作者对“减少 hallucination”的重视。

---

### 3.2 三个核心模块

#### （1）Threat Intelligence Retrieval Engine

这是 CTI 检索模块。

它基于 RAG 从威胁报告中提取：

* OS
* Processes
* Files
* IP addresses
* 背景攻击描述

目的就是把“自然语言威胁报告”翻译成“机器可查的调查线索”。

#### （2）System Data Retrieval Engine

这是系统数据查询模块。

它直接对 provenance 数据库执行 SQL 查询，并且是**类型感知的**：

* 查进程用进程类模板；
* 查文件用文件类模板；
* 查 IP 用网络实体模板。

作者强调为什么不能用一个通用查询：因为 provenance 里不同实体的语义完全不同。进程靠命令/路径识别，文件靠路径识别，网络流量靠 IP:port 识别。如果混查，容易语义错乱。

#### （3）Filtration Engine

这是过滤模块。

即使 SQL 已经比较精准，返回结果仍可能有大量高频、正常、无害事件。
所以作者又加了一层 **AutoEncoder 异常过滤器**：

* 把 SQL 返回的候选事件编码成特征向量；
* 用在 benign 数据上训练好的 AutoEncoder 计算重构误差；
* 重构误差高的，认为更“罕见”、更值得关注；
* 最终只把高信号事件传给 LLM 推理。

这个模块的作用非常关键：
**它不是做最终检测，而是做上下文压缩。**
换句话说，AutoEncoder 的主要贡献不是“判攻击”，而是帮 LLM 少看废话、少烧 token、少陷入上下文爆炸。

## 4. 这个系统到底怎么工作

论文第 4～7 页描述得很清楚。我把完整流程翻译成更直观的话：

### 第一步：用户提问

例如：

> “根据 Drakon dropper 的攻击特征，我有没有被攻击？”

系统先识别这是一个“基于威胁情报进行取证判断”的问题。

### 第二步：RAG 从 CTI 报告中抽 IOC

系统可能从报告中抽到：

* 进程：`profile`, `gtcache`
* 文件：`/tmp/memtrace.so`, `/var/log/mail`, `/var/log/xdev`, `/var/log/wdev`
* IP：`104.228.117.212:80`, `141.43.176.203:80` 等。

### 第三步：去 provenance 库中查这些 IOC

例如查到：

* `/home/admin/profile` 写了 `/var/log/mail`
* 随后又把 `/var/log/mail` unlink 删除
* 对 `/var/log/xdev`、`/var/log/wdev` 也有类似 write → unlink 行为

这就是非常典型的**痕迹清除 / 伪装 / 清理痕迹**行为模式。

### 第四步：如果证据不够，就 follow-up

比如：

* 找到了 `/var/log/xdev`，但没找到 `/var/log/wdev`；
* 或者初步怀疑和 Firefox 有关，但链条还不完整；

Follow-Up Agent 就会继续查，直到把“写入—删除—网络外联—可疑父子关系”等证据拼起来。

### 第五步：Safety Agent 审计

它会问：

* 你说“被攻击了”，有没有 edge IDs 支撑？
* 你说“像浏览器入口”，是不是证据还只是猜测？
* 你推荐“立刻封禁 IP”，证据够不够强？

如果不够，就退回补证据。

### 第六步：输出最终取证摘要

摘要不仅有“结论”，还有：

* 观察到的 TTP
* 选定的关键证据
* 没找到的负向指标
* 对当前结论的置信度
* 立即响应建议

论文第 6 页展示了一个 final assessment 示例，这是非常接近真实 DFIR 报告的写法。

## 5. 这篇论文的创新点在哪里

我认为主要有 4 个创新点。

### 5.1 把 LLM 用成“调查编排器”，不是“答案生成器”

很多安全场景里，LLM 最危险的点是会编。
这篇论文的高明之处在于：**它不让 LLM 直接负责事实，而是让 LLM 负责计划、调度、补查、组织证据。**

事实必须来自：

* CTI 检索
* provenance SQL
* artifact lookup
* event resolver

所以它把“语言模型的强项”与“数据库的可验证性”结合了起来。

### 5.2 verification-first 设计非常适合安全取证

安全领域最怕“说得像真的，但验不了”。
论文明确要求每个关键结论都要能回指到 edge / node / event。
这比很多“检测+解释”工作更务实，因为它真正服务于分析员要写报告、要复核、要做响应。

### 5.3 把 RAG 和 provenance 查询深度绑定

传统 RAG 只能把报告内容检出来，但未必能映射到系统事实。
这篇论文让 RAG 只负责“找线索”，不负责“给结论”；真正的结论还得经过 provenance 数据验证。
这就把“文本层证据”和“系统层证据”打通了。

### 5.4 把可扩展性问题转化成“查询规划问题”

作者一个很重要的观点是：
provenance 太大，不能什么都 embed、什么都送进 LLM。
所以正确做法不是蛮力吃全量数据，而是：

* 先靠 CTI 缩小搜索空间；
* 再用类型感知 SQL 精确查；
* 再用 AutoEncoder 滤掉高频 benign 事件；
* 最后只让 LLM 看少量高价值证据。
