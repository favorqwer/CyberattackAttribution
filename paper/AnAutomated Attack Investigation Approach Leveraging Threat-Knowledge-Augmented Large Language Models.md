# 一、这篇论文在做什么

这篇论文提出了一个自动化攻击调查框架 **ANANKE**。它的目标不是“实时拦截攻击”，而是当安全系统已经产生告警之后，帮助分析员从**海量主机审计日志**里还原完整攻击链，并自动生成可读的调查报告。论文的核心观点是：

1. 传统基于规则的方法太依赖人工，难适应新攻击。
2. 传统基于深度学习/图学习的方法往往依赖历史训练数据，跨平台泛化差，面对新攻击常要重训。
3. LLM 虽然擅长理解日志和生成摘要，但单靠它本身，难以在超长日志里保持跨阶段、跨主机的因果连续性。
4. 所以作者把 **LLM + 检索增强生成（RAG）+ Kill Chain威胁知识库 + 溯源图局部扩展** 结合起来，做成一个面向攻击调查的闭环系统。

论文把这个系统称为**首个基于LLM的自动化攻击调查框架**，并报告在 15 个攻击场景上取得平均 **TPR 97.1%**、平均 **FPR 0.2%**，明显优于对比方法 ATLAS（平均 TPR 79.2%，平均 FPR 29.1%）。

# 二、先理解背景：什么叫“攻击调查”

论文讨论的是 **attack investigation**，你可以把它理解成：

* IDS/EDR 给了一个告警点，例如某个 IP、某个恶意进程、某个域名。
* 安全分析员需要从这个点往前追、往后追：

  * 它怎么进来的？
  * 做了什么？
  * 有没有持久化？
  * 有没有横向移动？
  * 最终有没有窃取数据？
* 最后拼出完整“攻击故事”。

论文把日志抽象成 **subject-action-object** 三元组，例如：

* 进程 → 读/写 → 文件
* 进程 → 连接 → IP
* 进程 → 启动 → 进程

再把这些事件连成一个**溯源图（provenance graph）**。节点是系统实体（进程、文件、IP、网站等），边是带时间戳的交互事件。这样做的好处是可以同时保留三种关键信息：

* **因果性**：谁触发了谁
* **时间性**：先后顺序
* **语义性**：字段本身带有人类可理解的含义

论文还引入 **Cyber Kill Chain** 作为攻击阶段框架：侦察、武器化、投递、利用、安装、命令控制、达成目标。作者认为攻击天然是分阶段推进的，因此 Kill Chain 很适合作为 LLM 推理时的结构化先验。

# 三、这篇论文真正要解决的痛点

## 1. 新攻击一来，旧模型容易失效

传统学习方法依赖既有攻击模式，面对全新手法时常需要重训；而重训成本高，还可能带来“灾难性遗忘”。论文特别举例说明：如果攻击者从利用 Flash 漏洞切换成 SMB 服务漏洞，再加上向正常进程里注入恶意代码，老模型很可能适应不了。

## 2. 跨平台差异大

Windows 和 Linux 的日志机制、语义、字段分布都不同。像 ATLAS 这种方法需要针对不同系统建立不同词表或特征表示，迁移能力有限。论文中的图 3 显示，作者尝试把 Windows 和 Linux 的日志语义混在一起训练统一模型时，平均 TPR 从 87.6% 降到 57.1%，说明传统学习范式对平台特征很敏感。

## 3. 日志太多，攻击事件太少

攻击相关日志只占极小一部分，典型是“大海捞针”。如果做全图遍历，容易把大量 benign 事件也卷进来，导致误报高、成本高。

## 4. 输出不够“调查员友好”

很多方法最后只给出一堆可疑片段，而不是完整、可读、能直接用于调查报告的叙事。分析员还得自己再拼接攻击路径。

# 四、ANANKE 的核心思想

一句话概括：

**先把已知攻击经验整理成“按 Kill Chain 组织的威胁知识库”，再让 LLM 在调查过程中，围绕告警点做局部图扩展，并在每一步从知识库中检索最相关的攻击知识来辅助推理，逐步扩展出完整攻击链。** 

它分成两个阶段。

---

# 五、阶段一：构建 Kill Chain 威胁知识库

这一阶段不是拿目标机器的日志来调查，而是先拿**已知攻击场景**的数据，构建一个可动态更新的知识库。

## 第一步：抽取恶意相关事件

作者假设已知攻击样本里有：

* 全量日志集合 (L)
* 已标注的恶意实体集合 (E_{mal})

系统把日志也转为三元组，然后只保留那些与恶意实体有因果或语义关联的日志，形成攻击相关轨迹集合 (T)。这样做是为了把知识库聚焦在“真正有用的攻击行为”上，避免被无关系统活动稀释。

## 第二步：按 Kill Chain 进行阶段化标注

对每一段攻击轨迹，LLM 会根据结构化提示词，把它切分成若干阶段单元 (k_i)。每个单元包含两部分：

* **元数据** (m_i)：

  * Phase：所属 Kill Chain 阶段
  * Behavior：行为摘要
  * Entities：关键恶意实体
  * Neighbors：前后相邻阶段的预测描述
* **事件序列** (t_i)：该阶段对应的按时间排序的日志序列

这里最关键的不是简单分块，而是**按攻击阶段分块**。作者认为这比普通的“固定窗口切片”更好，因为攻击本来就是分阶段推进的，这种结构更贴近真实攻击逻辑，也更利于后续 LLM 推理。

## 第三步：向量化与索引

由于每段序列可能太长，作者会把阶段序列再分成最多 **20 个事件**的小子序列，然后做 embedding，连同元数据一起存进向量数据库。这样后续就可以根据当前可疑序列，从知识库里检索最相似的攻击知识单元。

### 这一阶段的意义

这一步本质上是在做“**把已知攻击经验结构化、检索化**”。

它的好处有三个：

1. 不需要重训大模型，只要往知识库里追加新攻击单元即可。
2. 推理时不是让 LLM 凭空猜，而是有外部威胁知识作为参考。
3. 知识是按攻击阶段组织的，因此更适合做跨步骤的因果重建。

# 六、阶段二：真正开始调查目标主机

这一阶段输入的是目标主机/目标环境中的原始日志，以及一个初始告警点。论文架构图（第 6 页图 4）把它拆成三个模块：**邻接优先扩展、因果推理、报告生成**。图 6 还展示了从告警节点向周边可疑节点逐步递归扩展的过程。

# 七、模块一：邻接优先扩展（Adjacency-Prioritized Expansion）

## 1. 先把调查对象构造成溯源图

目标环境日志被组装成一个大的 provenance graph。节点是系统实体，边是带时间戳的交互。这个图可能覆盖几天活动，包含几十万事件和上万个节点。

## 2. 从告警节点出发

调查从初始告警对应的节点开始，把这个节点放进“可疑节点队列”。

## 3. 每次只取“一跳邻域”

这一步非常重要。系统不会像传统方法那样一口气往前往后爆炸式全图遍历，而是：

* 从可疑节点队列里取出一个节点 (v)
* 只拿它的一跳邻居
* 形成一个局部子图 (G_{adj}(v))

## 4. 把局部子图转成时间序列

因为 LLM 更擅长处理顺序文本，而不是图结构，所以系统把这一小块邻接子图里的边按时间排序，再切成长度受限的小序列，放到“上下文队列”里，等待推理模块处理。

### 为什么这一设计很关键

因为它同时解决了两个大问题：

* **避免依赖爆炸**：不把整个因果链一下子全部展开
* **适配上下文窗口**：LLM 每次只看局部、紧凑、按时间排列的可疑上下文

你可以把它理解成：
不是让 LLM 一口吃掉整片森林，而是每次只给它看“当前这棵树附近最可疑的几根枝条”。

---

# 八、模块二：迭代因果推理（Iterative Causal Reasoning）

这是论文最核心的部分。

## 1. 对当前可疑事件序列做检索

系统从上下文队列中弹出当前序列 (s^{(t)})，先做 embedding，然后和知识库中所有知识单元比较相似度，用余弦相似度等方式找出最相关的威胁知识单元 (r^{(t)})。

检索出来的知识单元里不仅有示例事件，还有：

* 当前所属 Kill Chain 阶段
* 这一阶段行为的自然语言摘要
* 关键实体
* 前后相邻阶段的描述

这一步相当于在问：
**“我现在看到的这段局部日志，最像攻击流程中的哪一种阶段？”**

## 2. 结合历史摘要做推理

LLM 的输入不只是当前序列和检索结果，还包括**前几轮的推理摘要**。作者设计了一个 reasoning cache，缓存每一轮结果：

* (M^{(t)})：这一轮新识别的恶意节点
* (B^{(t)})：这一轮识别出的攻击行为描述
* (H^{(t)})：到这一轮为止的攻击路径摘要

于是 LLM 每次推理时能同时看到：

* 当前局部可疑序列
* 从知识库检索到的相似攻击知识
* 历史上已经推断出的攻击链摘要

这样就能维持**跨轮次、跨阶段的因果连续性**。

## 3. 把新发现的恶意节点重新送回去扩展

如果 LLM 在这一轮判断某些节点很可疑，它们会被送回“可疑节点队列”，下一轮就从这些新节点继续提取邻接子图、继续检索、继续推理。

### 这形成了一个闭环

也就是：

1. 局部扩展
2. 知识检索
3. LLM 推理
4. 发现新可疑点
5. 再次局部扩展

直到上下文队列被处理完为止。

### 这套设计为什么比“直接把大日志喂给 LLM”更强

因为单纯大模型有两个问题：

* 看不下全部日志
* 看完了也不一定记得前面与后面之间的因果链

而作者通过“**局部图扩展 + 显式缓存 + 分阶段知识检索**”，把调查问题拆成一系列小而连续的推理任务。这样更像人在做案件侦查：先看一个线索，再根据经验判断，再决定下一步查谁。

---

# 九、模块三：攻击故事生成（Attack Story Generation）

当所有上下文都处理完后，系统把 reasoning cache 中所有轮次的结果拿出来，交给 LLM 统一生成最终报告。这个生成提示会显式要求：

* 按时间顺序组织
* 把因果关系串起来
* 用分析员能读懂的自然语言表达
* 标上 Kill Chain 阶段

因此最终输出不是一堆零散可疑事件，而是一份完整的“攻击叙事报告”。

这也是论文和很多 prior work 的一个明显区别：
**它从一开始就把“生成调查报告”作为系统目标之一，而不是只做事件分类。**

# 十五、这篇论文真正的创新点是什么

我认为可以总结成四点。

## 1. 把“攻击知识”从模型参数里搬到外部知识库

它不是指望把所有攻击知识都学进模型，而是把知识显式地存成可检索的阶段化单元。这样新攻击来了，可以直接加新知识，不必重新训练。

## 2. 用 Kill Chain 给 RAG 提供结构化约束

很多 RAG 只是普通语义检索；这篇论文更进一步，用攻击生命周期来组织知识，让检索出来的不只是“像”，而且更符合阶段逻辑。

## 3. 用“局部图扩展 + 迭代推理”替代一次性全局分析

这是解决超长日志、依赖爆炸、上下文窗口限制的关键。

## 4. 从设计目标上就重视“报告生成”

它不仅要检测，还要生成 analyst-ready narrative，这使它更贴近现实取证场景。
