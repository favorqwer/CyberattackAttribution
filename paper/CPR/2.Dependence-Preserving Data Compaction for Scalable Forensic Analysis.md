# 1. 这篇论文到底在解决什么问题

论文关注的是**长期攻击（APT）发生后，如何对海量审计日志做法证分析**。
难点不只是“存不下”，更是“分析太慢”：

* 企业里 OS 审计日志会记录进程、文件、网络连接、IPC 等之间的大量读写关系；
* 法证分析常见任务是：

  * **Backward analysis**：从一个可疑对象往回找，找到攻击入口；
  * **Forward analysis**：从入口往前找，找到受影响范围。
* 这些分析本质上都是在**依赖图**上找“因果可达路径”。

论文的关键贡献是提出三类“依赖保持”的日志压缩准则：

* **CD**：Continuous Dependence preservation
* **FD**：Full Dependence preservation
* **SD**：Source Dependence preservation

以及一套高效实现手段，使得这些压缩不必直接在“带时间戳的图”上做，而是先转换为“版本图”，再用局部规则在线处理。

---

# 2. 基础模型：什么叫依赖、可达、法证分析

论文把审计日志看成一个**时间戳依赖图**：

* 节点：主体/客体

  * 主体：进程
  * 客体：文件、网络连接、pipe 等
* 边：事件（read / write / load / execute 等）
* 边方向：按**信息流方向**
* 边带时间戳。

## 2.1 因果路径（causal path）

不是普通图上的任意路径都算依赖，必须满足**时间不倒流**。

论文定义：若存在路径
( e_1, e_2, ..., e_n )
并满足对所有相邻边都有：

[
start(e_i) \le end(e_{i+1})
]

那么这条路径是**causal path**，表示前一个事件的影响有可能流到后一个事件。

## 2.2 两种可达

### Forward reachable at time t

( u@t \rightarrow v )

表示：u 在时刻 t 的状态，可能影响到 v。
要求整条 causal path 上每条边都发生在 t 之后或覆盖 t。

### Backward reachable at time t

( u \rightarrow v@t )

表示：v 在时刻 t 的状态，可以被 u 解释/追溯到。
要求整条 causal path 上每条边都发生在 t 之前或覆盖到 t。

这就是法证分析的数学基础：

* backward：找来源
* forward：找影响面

# 3. CD / FD / SD 三者到底差在哪里

---

## 3.1 CD：Continuous Dependence（连续依赖保持）

### 定义直觉

**最严格。**

要求压缩前后，对**任意两个节点、任意时刻**，forward/backward reachability 都完全一样。
换句话说：你不能只保留“最终能否到达”，而必须保留“每一个时刻的依赖关系”。

### 直观理解

如果一个文件 F 在 t=3 时还不能影响 H，但压缩后变成能影响 H 了，那就违反 CD。

### 问题

这个定义太强，导致很多本来“法证上无关紧要”的差异也不允许。

论文举的关键例子是：

* 某文件 F 在一段时间里根本没变化；
* 进程 S 多次从 F 读，又多次往别处写；
* 从时刻细节上看，某些中间时刻的 reachability 可能略有变化；
* 但对法证来说，F 若能影响，通常是“从最初就可能影响”，中间某个空档时刻是否精确一致，其实没那么重要。

### 论文里的定位

作者指出 Xu et al. 的 full-trackability equivalence 本质上类似一种**更局部化的 CD**，论文把它称为 **LCD**。
LCD 只看节点局部入边/出边排列，不看全局图可达性，因此能压缩的情况更少。

---

## 3.2 FD：Full Dependence（完全依赖保持）

### 核心想法

不要要求“每个时刻都一样”，只要求在**节点获得新祖先依赖的时刻**保持正确。

作者定义：

* ( Anc(v, t) )：时刻 t，v 的祖先集合
* ( NewAnc(v) )：使得 ( Anc(v,t) ) 发生扩张的那些时刻，也就是“v 获得新依赖来源”的时刻。并且定义 0 一定包含在里面。

### FD 的正式含义

压缩后必须保证：

1. 对任意 u、v，**u 在 NewAnc(u) 这些关键时刻**到 v 的 forward reachability 不变；
2. 对任意 u、v，**v 在任意时刻**回溯到 u 的 backward reachability 不变。

### 直觉

FD 允许你忽略一些“中间时刻”的细微差别，只要：

* 回溯结果完全不变；
* 正向传播在“u 刚获得新依赖、因此可能刚被污染”的关键时刻不变。

### 为什么这对法证是合理的

因为节点不会“凭空被攻陷”，它只能在某个时刻由于读入了新东西，才新增依赖。
所以真正重要的是：

* **什么时候第一次多了新的可疑祖先**
* 而不是“两个事件之间的空白时刻里 reachability 有没有细微差别”

---

## 3.3 SD：Source Dependence（源依赖保持）

### 核心想法

进一步放宽：法证里最常见的流程其实是

1. 先 backward 找到**source node**（入口源）；
2. 再从这些 source 做 forward 找影响范围。

那就没必要保留“任意内部节点之间”的依赖，只要保留：

* 从**源节点**到各节点的 forward reachability
* 各节点回溯到**源节点**的 backward reachability

即可。

### source node 是什么

没有入边的节点，比如：

* 网络连接源
* 审计开始前就存在的文件
* 早先启动的进程
* 外设输入 / 用户输入 等。

### SD 比 FD 更激进

FD 要保所有节点对之间的关键依赖；
SD 只保“源 → 任意节点”的依赖。

所以 SD 压缩率更高。实验里平均：

* LCD：1.8×
* FD：7×
* SD：9.2×

# 4. 真正的实现核心：把时间图变成“版本图”

这是整篇论文最重要的工程思想。

因为如果直接在带时间戳图上判断“某条边是不是冗余”，你可能要反复检查全图路径，开销很大。
论文的办法是：

> 把每个对象/主体拆成多个“版本节点”，从而把“时间因果”编码进普通图结构里。

这样后续压缩就能用普通图 reachability 或局部规则近似实现。

---

## 4.1 Naive Versioned Graph（朴素版本图）

### 规则

每当一个节点 v 收到一条新的入边，就新建一个版本 ( v^t )。

设原始时间戳边是 ((u, v, t))，则：

1. 为 v 新建版本 ( v^t )
2. 从 u 的“t 之前最新版本” ( u^{<t} ) 连到 ( v^t )
3. 再从 v 的旧版本 ( v^{<t} ) 连到 ( v^t )

这样，v 的各个版本就形成一条时间链。

### 为什么可行

论文证明：

* 在原始时间图中的 forward/backward reachability，
* 可以对应为版本图中的普通路径可达。

### 缺点

会产生**版本爆炸**。
实验里 naive 平均一个节点会产生 **25.58 个版本**，Linux Desktop 上甚至到 **68.65 个版本/节点**。

所以必须进一步优化。

---

# 5. FD 是怎么实现的

论文真正实现 FD，不是直接检查 FD 定义，而是在 BuildVer 基础上叠加几种优化。
核心是这四个：

* REO
* REO*
* RNO
* CCO

其中实际工程上主要用的是 **REO + RNO + CCO**；
REO* 理论上更强、更接近 FD 最优，但太贵，实验里收益不大。

---

## 5.1 REO：Redundant Edge Optimization（冗余边优化）

### 思想

当你要加入一个新事件 ((u, v, t)) 时，先看：

> 当前 u 的最新版本，是否已经直接连到某个 v 的版本？

如果已经有了，就说明“u 对 v 的这类依赖已经表达过了”，这条新边可以丢掉，而且通常也不用新建 v 的新版本。

### 为什么安全

对 FD 来说，如果这条边不会给 v 引入新的祖先依赖，那它不是关键的新依赖获取点，可以省掉。

### 工程意义

REO 是最重要、最便宜的优化之一。
它尤其擅长压缩：

* 一个进程反复读同一网络连接
* 一个进程反复写同一个输出文件
* pipe 的反复写/读
* 多个进程对日志文件的追加写等。

### 可理解成伪代码

```text
for each event (u, v, t):
    u_latest = latest_version(u)
    v_latest = latest_version(v)

    if exists direct edge u_latest -> some_version_of(v):
        discard event
    else:
        continue to RNO / version creation
```

---

## 5.2 REO*：Global Redundant Edge Optimization（全局冗余边优化）

### 思想

REO 只查“是否已有直接边”；
REO* 更强，查的是：

> u 的最新版本是否已经是 v 的祖先（即存在任意路径）？

如果已经可达，那么这条新边也不引入新的依赖来源，可以丢掉。

### 理论地位

论文证明：

* BuildVer + RNO + REO* 能保持 FD；
* 而且对 FD 来说是**最优的**：再删就会破坏 FD。

### 为什么工程里不主推

因为它要做祖先查询，可能接近全图搜索，代价较高。
作者实验发现比 REO 多带来的收益不明显，所以实现里主要还是 REO。

---

## 5.3 RNO：Redundant Node Optimization（冗余节点优化）

### 思想

即使某条边不能删，也不一定要新建版本。

假设 v 当前最新版本是 (v^{r,s})。
如果准备因为新事件在 t 创建新版本，但发现：

> 当前版本 (v^{r,s}) 还没有任何后代（没有出边）

那就没必要另建新版本，可以直接把它扩成 (v^{r,t})。

### 直觉

为什么可以这么做？

因为新旧两个依赖状态虽然不同，但如果这个版本还没有“传播出去”影响别人，那把它们合并不会误导其后代的回溯关系。

### 注意点

RNO 可能改变“从 v 本身出发的 backward reachability”，所以论文说需要在某些场景保留边时间戳，用于回溯时裁剪伪依赖。
但对 v 的后代而言，这种问题不会出现，因为后代都是在 v 的结束时间之后才产生的。

### 可理解成伪代码

```text
if event survived REO/REO*:
    v_latest = latest_version(v)
    if out_degree(v_latest) == 0:
        extend timestamp interval of v_latest to include t
    else:
        create new version v^t
        add chain edge old_v -> new_v
        add event edge from u_latest -> new_v
```

---

## 5.4 CCO：Cycle-Collapsing Optimization（环折叠）

### 背景

循环依赖会导致版本数暴涨。比如：

* 一个进程既写某文件又读回该文件
* 两个进程双向通信

这些循环在 provenance / forensic 里都很常见。

### 做法

在加边前检查是否形成环；如果形成，则可折叠/跳过这条边。
论文实现里只检查**两节点环**，因为：

* 全局环检测太贵
* 实验发现两节点环已经覆盖了大多数实际版本爆炸来源。

---

## 5.5 FD 的完整实现流程

综合起来，一个在线处理事件流的 FD 算法可以理解为：

### 输入

按时间顺序到来的审计事件 ((u,v,t))

### 状态

* 每个实体当前最新版本
* 版本图结构
* （可选）有限窗口内的祖先/父边信息
* 用于 CCO 的小环检测状态

### 处理流程

```text
for each event (u, v, t):

    1. 先做 CCO 检查
       if adding edge causes 2-node cycle that should collapse:
           discard or collapse
           continue

    2. 做 REO / REO*
       if u_latest already directly reaches (REO) or ancestrally reaches (REO*) v:
           discard event
           continue

    3. 做 RNO
       if v_latest has no descendants:
           extend current version interval of v_latest to include t
           add needed incoming relation
       else:
           create new version of v
           connect old_v -> new_v
           connect u_latest -> new_v

    4. 更新 latest pointers / metadata
```

### 实际实现上的近似

作者为了保证速度，对 REO 不是全图无限查，而是设置一个 **FD window size k**，只检查有限数量的边。
这样每条事件处理复杂度是 (O(k))，整体是线性的。

### 效果

* (FD=25) 到 (FD=100) 基本就是不错折中；
* Linux Desktop 在 (FD=25) 时处理 7200 万条记录只要 84 秒，约 **86 万事件/秒**。

# 6. SD 是怎么实现的

SD 的实现思路和 FD 不同，它不是主要靠版本祖先判断，而是直接维护**源集合**。

---

## 6.1 SD 的核心数据结构：Src(v)

对每个节点 v，维护一个集合：

[
Src(v) = \text{所有能到达 v 的 source nodes}
]

初始化时：

* 如果 v 自己就是 source，则 ( Src(v)={v} )
* 否则为空。

---

## 6.2 处理新事件 (u, v, t) 时怎么做

在加入事件前，检查：

> ( Src(u) \subseteq Src(v) ) 是否成立？

### 情况 1：成立

说明所有能影响 u 的源，v 都已经有了。
那这条边不会给 v 带来任何新的“源依赖”，所以可以直接丢掉。

### 情况 2：不成立

说明 u 携带了新的源，v 之前没有。
那必须保留这条边，并更新：

[
Src(v) := Src(v) \cup Src(u)
]

这样以后别人再向 v 连边时，才能判断是否还有新的 source 进入。

---

## 6.3 SD 在工程上怎么和 FD 组合

论文实现不是“只跑 SD”，而是：

1. 先做 FD 的优化（REO / RNO / CCO）
2. 若边在 FD 下还不能删
3. 再用 SD 的源集合规则检查能不能进一步删

所以 SD 的压缩率永远不会比 FD 差。

---

## 6.4 SD 的伪代码

```text
for each event (u, v, t):

    # first try FD-style reductions
    if removable_by_REO_or_RNO_or_CCO:
        discard or merge
        continue

    # then try SD
    if Src(u) subset_of Src(v):
        discard event
    else:
        keep event
        Src(v) = Src(v) union Src(u)
        do version handling as needed
```

---

## 6.5 SD 为什么正确

论文给了归纳证明，核心逻辑很直白：

* 任何时刻，(Src(v)) 都精确表示“当前能回溯到的所有源”；
* 只有当新边把“新的源”带给 v 时才保留；
* 所以不会漏掉任何 source dependence；
* 反过来，只要边被 SD 丢掉，就说明它不改变任何源可达关系，因此对“先 backward 找源、再 forward 看影响”的法证流程没有影响。

### 最优性

如果 SD 保留了一条边，必然因为它引入了至少一个新 source。
这条边再删，source dependence 就变了。
所以作者说 SD 也是**最优的**。

# 7. 那 CD 怎么“实现”？

严格说，这篇论文没有把 CD 做成它们主推的工程实现；它更多是一个**理论基线/参照物**。

论文的观点是：

* CD 很强，定义上合理；
* 但若直接依据 CD 做实现，需要频繁检查全局 reachability；
* 在时间戳图上这样做很贵，不适合大规模在线处理。

所以作者没有重点实现一个“通用 CD 算法”，而是：

1. 说明 Xu et al. 的 full-trackability 可视为一种**局部 CD（LCD）**
2. 重实现了 Xu 的算法，作为实验对照
3. 然后说明 FD/SD 更强，因为它们利用了全局图性质，而不只是节点局部边模式。

---

## 7.1 LCD（也就是 Xu 那套）为什么弱

LCD 的约束本质是：

* 只看某个节点周围的入边/出边时间区间是否交错；
* 若交错，就不敢合并。

这导致一种常见模式完全压不动：

```text
read(A); write(B); read(A); write(B); ...
```

因为每两次 read(A) 中间都有 write(B)，
LCD 只看局部就会说“不能合并”。

但 FD 会进一步看全局：
若 A 在这段时间根本没变，那么多次 read(A) 不会给进程带来新的祖先依赖，所以可以放心合并。

---

# 8. 三种算法的本质差异，一句话总结

## CD

“每个时刻的依赖都别变。”
最严格，最难实现，压缩最差。

## FD

“法证真正重要的依赖别变：回溯永远不变；传播在新依赖到来时不变。”
是论文主力方案，兼顾正确性和实用性。

## SD

“我只关心源头到目标的法证链，不关心所有内部节点对之间的依赖。”
更激进，压缩率最高，适合典型调查流程。

---

# 9. 实验结果怎么看

论文实验里，平均事件压缩因子：

* **LCD：1.8×**
* **FD：7×**
* **SD：9.2×** 

对磁盘日志大小：

* CSR 基础格式已比原日志小约 **8×**
* 加上 FD 后平均 **35.3×**
* 加上 SD 后平均 **41.4×**。

对内存图表示：

* 平均不到 **5 bytes / 原始事件**
* 最大数据集 7260 万事件，只用了 **111MB（FD）**。

版本数方面：

* naive：平均 **25.58 版本/节点**
* FD：平均 **1.26**
* SD：平均 **1.14**。

这说明论文的关键不只是“删边”，更是**通过版本优化把版本爆炸抑制住了**。

# 10. 你可以把这篇论文的算法框架记成这个图景

## 原始问题

带时间戳依赖图太大、太难算

## 变换

先做版本化，把时间编码到版本节点

## 再压缩

* FD 路线：

  * REO：已有直接依赖就删边
  * REO*：已有祖先路径就删边（理论更强）
  * RNO：没后代就不新建版本
  * CCO：小环折叠
* SD 路线：

  * 在 FD 基础上再维护 Src(v)
  * 若新边不引入新 source，就再删掉

## 输出

* 紧凑日志
* 紧凑内存图
* backward / forward 法证结果不变（FD），或对源调查流程不变（SD）
